Die Ausgangslage

Der Prozess steht im Repo,
nicht in Köpfen

  • Jede nichttriviale Änderung wird zuerst spezifiziert — erst danach entsteht Code.
  • Der Ablauf ist per ADR verbindlich beschlossen, nicht Geschmackssache pro Entwickler.
  • .claude/ ist eingecheckt: Wer den Branch auscheckt, hat dieselben Skills, Regeln und Gates.

Fundament·1 von 4

CLAUDE.md ist die Betriebs­anleitung

  • Drei Dateien, je nach Ort: Root für echt Monorepo-Weites, dazu eine pro App.
  • Wird bei jeder Session automatisch geladen — eine Änderung wirkt sofort für alle.
  • Harte Grenze: unter 200 Zeilen. Wird es mehr, sagt Claude Bescheid statt zu wachsen.

CLAUDE.md ← monorepo-weit
apps/backend/CLAUDE.md ← Spring Boot
apps/frontend/CLAUDE.md ← Angular

Vor Arbeit in einer App die App-Datei lesen — Root wiederholt sie absichtlich nicht.

Fundament·2 von 4

Was in .claude/ liegt

  • skills/ — 13 getrackt: 5 eigene Wrapper plus 7 generierte openspec-* und new-skill.
  • commands/opsx/ — von der OpenSpec-CLI erzeugt, reine Generate-Ausgabe.
  • rules/ — pfadgebundene Regeln, greifen automatisch beim Editieren: Handler, Mapper, Migrationen, Tests.
  • hooks/openspec-preflight.sh — prüft beim Session-Start die drei Voraussetzungen, die das Repo nicht pinnen kann.
  • settings.json geteilt · settings.local.json persönlich und gitignored.

Der Preflight warnt nur und endet immer mit 0. Stille heißt „alles gut“ — oder „lief nie“.

Fundament·3 von 4

openspec/ ist die geteilte Wahrheit

  • changes/ — was gerade in Arbeit ist, ein Ordner je Ticket.

Phase 1·Backlog

/startandplan <issue-nummer>

Ticket nehmen und durchdenken

  • Ticket sich selbst zuweisen, Branch task/67-slug schneiden — vor dem ersten Artefakt.
  • Prüft vorher hart: sauberer Working Tree, auf develop, nicht hinter origin.
  • Erzeugt die vier Artefakte im Dialog (opsx:explore + opsx:propose).
  • Öffnet den Draft-PR und setzt das Label Ready4Refinement.

Phase 2·Backlog

/refine <change-name>

Das Refinement-Meeting

  • Kein OpenSpec-Original — dieses Skill gibt es nur bei uns.
  • Jede offene Frage wird beantwortet: fachlich im proposal.md mit PO, technisch im design.md nur mit Devs.
  • Ergebnisse landen unter ## Decisions — inklusive Begründung, nicht im Meeting-Gedächtnis.
  • Setzt zum Abschluss das Häkchen und tauscht das Label auf Refined.
  • Ändert nie Code. Und die Lane bleibt in Backlog.

Phase 3·Ready → Waiting for Review

/implement <change-name>

Umsetzen, was spezifiziert ist

  • Verweigert, solange das Refinement-Häkchen fehlt — Gate 1.
  • Zieht das Ticket auf In Progress und arbeitet tasks.md ab.
  • Die Regeln aus .claude/rules/ greifen dabei je nach Pfad automatisch mit.
  • Am Ende: Draft-PR auf ready, Ticket auf Waiting for Review.
  • Ist auch der Rework-Pfad, wenn ein Review Änderungen verlangt hat.

Phase 4·In Review

/review <change-name>

Vier Augen, gegen die Spec

  • Ein anderer Entwickler übernimmt und zieht das Ticket auf In Review.
  • Geprüft wird die Implementierung gegen spec, design und tasks — plus die eigenen Findings des Reviewers.
  • Alles zusammen als ein Inline-Review am PR, nicht als Kommentarserie.
  • Ergebnis: zurück an den Autor (→ In Progress) oder frei zum Archivieren.

Überschreibt bewusst das eingebaute /review von Claude Code. Für ein Ad-hoc-Review am Arbeitsdiff: /code-review.

Phase 5·Sprint Done

/finish <change-name>

Archivieren heißt: Spec nachziehen

  • Verweigert, solange der PR nicht APPROVED ist — Gate 2.
  • opsx:sync faltet das Delta in specs/, der Change-Ordner wandert nach changes/archive/.
  • Danach Squash-Merge auf develop, Ticket auf Sprint Done.
  • Done setzt ein Mensch — erst zum Sprintende.

Ab hier ist der Change Vergangenheit: specs/ beschreibt den neuen Stand, das Archiv nur noch, wie er dorthin kam.

Warum es trägt

Zwei Gates, die niemand
versehentlich überspringt

  • Gate 1 · Refinement. - [x] Refinement complete im proposal — nur /refine darf es setzen, /implement bricht sonst ab.
  • Gate 2 · Approval. reviewDecision == APPROVED am PR — sonst archiviert /finish nicht.
  • Dazu die CI, pfadgefiltert pro App: ein roter Required-Check blockiert Approval und Merge ohnehin.

Beide Gates erzwingt die OpenSpec-CLI nicht — sie stehen im Text der Skills. Deshalb steht dort auch die Begründung, und deshalb liest man das Skill, wenn man es fährt.

Konventionen

Zwei Sprachen, ein Repo

  • Englisch: Artefakte, Specs, Code und Kommentare.
  • Deutsch: alles GitHub-seitige — Issues, PRs, Commit-Messages.
  • GitHub-Text bleibt kurz: Stichpunkte statt Prosa, kein Kontext den der Leser schon hat, keine Tabellen und Diagramme.
  • Ausführliches gehört in die Artefakte — dort gibt es keine Längenbegrenzung.
  • Commit-Prefix: nur openspec/changes/** → chore:; sobald openspec/specs/** dabei ist, ein echtes feat: / fix:.

Der Grund für „kurz“ ist erfahrungsgestützt: lange Kommentare werden im Team überlesen.

Fallstricke

Fünf Dinge, die einmal jeder falsch macht

  • Nie .claude/commands/opsx/ oder skills/openspec-* per Hand editieren — openspec update schreibt sie byte-genau neu.
  • Skills werden nur beim Session-Start entdeckt: nach einem Branch-Wechsel Session neu starten.
  • Der Ticket-Guard ^(feat|bug|task)-\d+- steht byte-identisch in allen fünf Skills — ändern heißt fünfmal ändern.
  • Ein Change-Ordner ohne Ticketnummer im Namen fällt aus der ganzen Automatik heraus.
  • Der Preflight-Hook warnt nur. Fehlende gh-Scopes merkt man erst, wenn ein Board-Move scheitert.
